# CLAUDE.md

## Project

qemu-system-generator: a systemd generator, in Rust with no dependencies
outside the standard library, that reads `.qemu` files and writes the
units that run them. The format is the deliverable; the man page in
`docs/qemu-systemd.unit.5.scd` is its specification and
`tests/expected/dryrun.txt` its conformance record.

**License**: copyleft-next-0.3.1. SPDX header on every source file.

## Principles

The backend section is a decoder. `[QEMU]` lines are QEMU options, key
= option name without its dash, value verbatim, order = file order. The
generator never translates, validates or reorders them, and holds no
list of QEMU options; QEMU is the validator and `man qemu-system` the
documentation. `[virtiofsd]` follows the same rule for virtiofsd. A
line the generator reads (`m=`, `machine=`, `uuid=`, `device=`) is still
emitted as written.

Zero tool at run time. The generator runs at `daemon-reload` and exits.
The generated units call only what the system ships: QEMU, virtiofsd,
`socat`, `varlinkctl`, `ssh`.

Generated output names the units and binaries it runs, never this
project, except the `# Automatically generated by` banner. Unit names
are `qemu-system@<name>.service` and `virtiofsd@<name>-<tag>`;
directories are named after those prefixes (`qemu-system/%i`,
`virtiofsd/%i`).

Automation is the third pillar: what the lifecycle needs (directories,
device access, control socket, registration, virtiofs wiring, locked
memory) is generated, never asked of the file.

The door stays open: `src/plan.rs` is launcher-neutral, `src/backend/`
decodes, `src/launcher/` emits. A second backend or launcher is a new
module, not a rewrite.

## Critical rules

### Never fabricate facts

Every QEMU option, virtiofsd option, systemd directive, specifier, path
and device-node name must be verified against `man`, `--help` or the
source tree (`~/src/qemu`, `~/src/systemd/systemd`,
`~/src/podman/podman`) before it is written into code, docs or
examples. Check the local trees before the web.

### Never cheat during verification

`tests/verify` and `cargo test` run from a clean build. Do not edit the
expected output by hand; run `tests/update-expected` and review the
diff.

## Conventions

### Rust

`#![forbid(unsafe_code)]`, `clippy::pedantic` clean with `--deny
warnings`, `cargo fmt`. Errors are enums with `Display` and
`Error::source()`, never strings. Newtypes (`UnitName`, `Tag`) validate
in `FromStr`. Values destined for unit text stay `String`; paths the
generator itself opens are `PathBuf`. The "why" of a shape belongs in
the commit body, not in a comment; a comment says what would tempt a
wrong cleanup.

### Long-form command options

`--symbolic` not `-s`, `--parents` not `-p`, in docs, scripts, README
and anything shown to the user. Exception: tools without a long form
(`ssh -o`, `ssh -i`).

### Prose

Avoid the em-dash and en-dash appositive style in all prose, including
documentation, code comments, and commit messages. Rewrite such
constructions as separate sentences, or use a colon, semicolon, or
parentheses instead.

Distinguish a tool's project name from its command: name the project in
plain text with its canonical spelling (QEMU, systemd, virtiofsd, Nix,
Cargo) and backtick the executable you run (`qemu-system-x86_64`,
`systemctl`, `cargo`). So "Cargo builds it", but "run `cargo test`".

### Documentation references

Reference QEMU, virtiofsd and systemd manuals only. `man qemu-system`,
`virtiofsd --help`, `man systemd.exec`, `man systemd.generator`.

### Technical identifiers in docs

Backtick-format directives with their trailing `=` (`ExecStart=`),
paths, options and file names. Plain text for tool names in prose
(QEMU, virtiofsd, systemd).

### Examples are generic

Paths under `/srv/`, relative image names that resolve in the state
directory, no user names or home-directory paths.

## Commit rules

All commits must follow these six rules.

1. One commit per change. Atomic commits only; do not mix unrelated
   changes, such as a spelling fix with a code change. When in doubt,
   leave spelling fixes out unless explicitly asked.

2. Write the subject as `subsystem: summary` in the imperative mood,
   where the subsystem names the area changed: `generator`, `backend`,
   `launcher`, `unitfile`, `search`, `plan`, `examples`, `tests`,
   `docs`, `nix`, `scripts`, `README`, `CLAUDE.md`, or
   `qemu-system-generator` for a cross-cutting change. Keep the whole
   subject within 75 characters, following the Linux kernel rule that
   the summary "must be no more than 70-75 characters"
   (Documentation/process/submitting-patches.rst). Aim short; never pad
   to fill the limit.

3. Sign off using the git-configured identity. Check it with
   `git config user.name` and `git config user.email`, then add a
   `Signed-off-by` trailer (`git commit --signoff`).

4. Mark AI-assisted work with an `Assisted-by: LLM` trailer ahead of the
   `Signed-off-by` that closes the message, as the kernel places it:

   ```
   subsystem: summarise the change in the imperative mood

   Plain-English description of what changed and why, wrapped at 75 columns.

   Assisted-by: LLM
   Signed-off-by: User Name <user.name@domain.org>
   ```

   Credit other contributors as the kernel's
   Documentation/process/submitting-patches.rst does ("When to use
   Acked-by:, Cc:, and Co-developed-by:"). The commit author is the
   primary author. A co-author gets a `Co-developed-by` immediately
   followed by their own `Signed-off-by`, which only they can give; the
   sign-offs run in the order the change passed through hands, so the
   last is always the committer's. Someone who wrote none of it but
   approves it gets an `Acked-by` or `Reviewed-by`, again only with
   their permission:

   ```
   Co-developed-by: Co Author <co.author@domain.org>
   Signed-off-by: Co Author <co.author@domain.org>
   Assisted-by: LLM
   Signed-off-by: User Name <user.name@domain.org>
   ```

   This is the kernel's own tag, adopted here for the same reason rule 2
   takes the kernel's subject limit: a contributor moving between this
   repository and the kernel should not have to keep two conventions in
   mind. The tag arrived in v7.0-rc1 with commit 78d979db6cef ("docs:
   add AI Coding Assistants documentation"), which added
   Documentation/process/coding-assistants.rst and defines the format
   as `Assisted-by: LLM [TOOL1] [TOOL2]`; 6252e5c1c20e ("docs: add an
   Assisted-by mention to submitting-patches.rst") then made the
   acknowledgment a submission requirement. The optional tool names are
   for specialized analysis tools actually run (coccinelle, sparse,
   smatch, clang-tidy); basic tools such as git, cargo, clippy and
   editors are never listed, so the bare `Assisted-by: LLM` is the
   usual form. No Co-Authored-By trailer.

5. No shopping-cart lists. Write the body as plain-English paragraphs,
   not bullet points or itemised lists, wrapped at 75 columns (trailers
   are exempt, as in the kernel), focused on helping a reviewer
   understand the implementation. The body carries only what `git show`
   cannot: the constraint that forced the shape, a decision and what it
   rules out, a measured result as the number.

6. Before committing, run the checks below. `scripts/check-style.sh`
   checks trailing whitespace, missing end-of-file newlines, SPDX
   headers, and HEAD's commit-message trailers and prose. Linked as the
   repository's commit-msg hook, `scripts/commit-msg` runs the message
   part before the commit lands:

   ```shell
   ln --symbolic --relative scripts/commit-msg "$(git rev-parse --git-path hooks)/commit-msg"
   ```

What a message, a doc or a comment says follows `docs/writing.md`, taken
from how the kernel's maintainers write: read two of its example commits
before writing one, and hand anything longer than a few lines to a
fresh-context editor with the brief there. `scripts/check-prose.py`, run
by `check-style.sh` and the commit-msg hook, refuses the phrasing they
almost never use.

Commit and push only when asked.

## Before committing

```shell
cargo fmt --check
cargo clippy --all-targets -- --deny warnings
cargo test
tests/verify
nix flake check
scripts/check-style.sh
```
